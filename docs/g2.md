# muxtower on Even Realities G2 (architecture, draft for review)

Goal: from the glasses, see which agent needs you, approve / deny / answer it, reply by voice, and read its last answer, for every session on a daemon, at home or away. Status: architecture only; implementation trade-offs are discussed after this is agreed.

## Platform facts that shape the design

- A G2 "app" is a web page running in the Even App's WebView on the phone (Chromium on Android, WKWebView on iOS); the glasses are a display + input client over BLE. **The phone screen shows nothing of the app**, so an app has no place to type a URL or a code.
- Display 576×288, monochrome, one proportional font, no font size; a full-screen text box holds ~400–500 characters; lists ≤ 20 items × 64 characters; one container receives input.
- Input: tap, double tap, swipe up/down, long press (temple or R1 ring); a system menu (tap, then long press) with ≤ 10 custom items.
- Microphone: 16 kHz PCM; no built-in speech-to-text for apps.
- Network: `fetch` and WebSocket, but only to origins listed in `app.json`; HTTPS in production; CORS is enforced as in any browser.
- Background: Android may suspend the WebView (WebSockets drop, memory is lost); no API to wake the display or notify.
- **The stock Even App already contains an agent UI, "Even Terminal".** It speaks a small HTTP + SSE protocol (reference server: `@evenrealities/even-terminal`, 0.10.5), pairs by scanning a QR code with the phone, renders transcript, tool calls, permission and question menus on the glasses, and does voice input itself.
- Prior art (14 projects surveyed): every bridge uses HTTP plus a push channel. Five speak SSE (four of them the Even Terminal protocol or a copy of it), six use WebSocket, one is plain HTTP; none needs anything but an HTTPS origin and a bearer token.

## Two ways onto the glasses

| | A. Even Terminal adapter (in the daemon) | B. Own Even Hub app (`muxtower-g2`) |
|---|---|---|
| Who renders | the stock Even App | our code, through SDK containers |
| Voice | the Even App | ours: stream PCM to the daemon, run ASR there |
| Pairing | scan a QR in the Even App | device-code flow (the app shows a code, you approve it on your phone) |
| Install | nothing to install | sideloaded private build (`.ehpk`) |
| Sessions | per connection, one agent type (claude *or* codex) | anything we design (an inbox across all sessions) |
| Protocol risk | Even's protocol is not documented; it can change with an Even App update | the SDK is public and versioned |
| Fits muxtower's thesis | server-side, API-first: the daemon learns one more protocol | a third client next to the web app and the CLI |

**Proposed decision: build A first; B only if A's limits matter in daily use.** A gets display, menus, voice and pairing from Even, and muxtower already has every piece of state the protocol needs. B stays possible later on the same API.

## A. The Even Terminal adapter

A new daemon domain, `daemon/src/muxtower/even/`, following the backend template (routes / service / port / adapter in separate files). It translates muxtower state into the protocol; it owns no state of its own except a per-session event buffer.

```
Even App (phone) ──HTTPS──► gate ──► Caddy ──► muxtowerd
   GET  /even/<provider>/api/events?token=…   (SSE)      even/routes.py  ─► even/service.py ─► bus, sessions, approvals
   GET  /even/<provider>/api/sessions|status|info|messages
   POST /even/<provider>/api/prompt|permission-response|question-response|interrupt
```

- **Mount point.** One base URL per agent type, `/even/claude` and `/even/codex`, because the Even App shows one agent type per connection. Each becomes its own entry in the Even App.
- **Event mapping** (muxtower → protocol):

| protocol event | from |
|---|---|
| `status` busy/idle | session state (busy ↔ busy; everything else idle); a snapshot is sent on connect |
| `permission_request` / `permission_result` | pending action in `needs_permission`, `needs_trust`, `plan_review`: tool name + command (hooks), options (screen menu) / the approval result |
| `user_question` / `question_answer` | `needs_answer`: questions (AskUserQuestion hook input) or the screen menu |
| `tool_start` / `tool_end` | PreToolUse / PostToolUse hooks (by `tool_use_id`) |
| `user_prompt` | UserPromptSubmit hook |
| `text_delta` + `result` | Stop hook `last_assistant_message`, sent as one block |
| `notification` | errors (`StopFailure`, API errors on screen) |

- **Inbound** maps onto existing services: `/prompt` → input (text + Enter), `/permission-response` and `/question-response` → approve with the chosen option or deny, `/interrupt` → Escape. Same audit log, same "re-read the screen before sending keys" rule.
- **Wire format** is byte-compatible with the reference server: `:ok` first, `id: N\ndata: …\n\n`, `:heartbeat` every 15 s, `retry: 2000`, a per-session ring buffer (in memory, 500 events, replay only on `needReplay=true`).
- **Auth.** The Even App sends its token as `?token=` (EventSource cannot set headers) and as a bearer. The adapter accepts a muxtower **device token** both ways, but only under `/even/`. The rest of the API keeps refusing `?token=`.
- **Pairing.** `muxtower pair --even [--provider claude|codex]` mints a device token named "Even App" and prints the Even-format QR: `https://<public_url>/even/claude?token=<token>&defaultProvider=claude&name=<daemon name>`. The token is in the QR by Even's design; it is revocable like any device.
- **Behind a gate.** The gate must let that token through: register it as a host-scoped API token (gate: `API_TOKENS`, `even:<token>@muxtower.example.com`), so both the bearer and `?token=` pass. An unregistered token in `?token=` would count as guessing.
- **Alerts while the glasses app is closed** need no adapter: muxtower's Web Push becomes a phone notification, which the Even App mirrors to the glasses when that app is selected under its Notification settings.
- **Sessions without hooks** (adopted panes) get status and screen-derived permission/question menus, but no transcript events.

### What the backend template asks of A

- Domain folder with four roles; the service never imports FastAPI or the SSE writer; the bus and the session/approval services are its ports.
- Every event is a Pydantic model (one per protocol type). The protocol is external, so its contract is a set of recorded fixtures from the reference server (`tests/fixtures/even/*.sse`). Our output must match them byte-for-byte, and a test fails when a field drifts.
- Background work: one bus subscription per connected client, cancelled on disconnect; dead clients are dropped on a failed write, as the reference does.
- No secrets in logs: the access-log filter also redacts `token=` under `/even/` (Caddy already strips `token`).

## B. Own Even Hub app (deferred)

If built, it follows the frontend template, adapted to a non-DOM UI:

- `glasses/`: Vite + TypeScript + `@evenrealities/even_hub_sdk`. There is no React renderer, because the screen is SDK containers. A page is a plain description (`{text, list, menu}`), and one renderer diffs it into `textContainerUpgrade` (no flicker) or `rebuildPageContainer` (layout change). The page primitives play the role of `components/ui/`, and the 576×288 limits play the role of tokens: lint-enforced character and item limits instead of colors.
- State: `@tanstack/query-core` for server state and `zustand/vanilla` for UI state (the template's split, without React). The data contract is the same generated OpenAPI client as the web app (`packages/api-client`).
- Pairing: device-code flow on the daemon (new endpoints), because the phone shows nothing. Voice: PCM over WebSocket to a new `/v1/asr` with a pluggable recognizer (local whisper by default).
- Network: `app.json` lists the daemon origin; gate token as in A.

## The auth template

Not applicable: muxtower has no user accounts. A daemon has one owner, and devices hold revocable tokens (pairing codes, `X-Muxtower-Auth`). The Even App is one more device. Nothing here needs fastapi-users, passwords or OAuth.

2. Gate: register the Even token in gate (`API_TOKENS`), or put `muxtower.example.com` in gate's observe mode (muxtower does its own auth; gate only counts its 401s)?

5. Codex: no hooks yet, so `/even/codex` would carry status and screen menus only.

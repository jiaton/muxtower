# muxtower on Even Realities G2 (architecture, draft for review)

Goal: one place, on the glasses and on the phone, for every coding agent the owner runs (Claude Code on the NAS, Claude Code on a MacBook, Codex anywhere, sessions started from the Claude desktop app or with `claude remote-control`). A session that needs you pops up; you can step into any session to approve, answer or reply by voice; long replies arrive as a short summary that the R1 ring scrolls through, with the full text one swipe away.

Status: decisions below are agreed in principle; implementation trade-offs are discussed next.

## Platform facts that shape the design

- A G2 app is a web page running in the Even App's WebView on the phone (Chromium on Android, WKWebView on iOS). It draws on the glasses through SDK containers (`@evenrealities/even_hub_sdk`) and can also show a **phone-side panel** (its own HTML, used for settings and fuller controls).
- Glasses display: 576×288, monochrome, one proportional font, no font size; ~400–500 characters per full-screen text box; lists ≤ 20 items × 64 characters; one container receives input.
- Input: tap, double tap, swipe up/down, long press (temple or R1 ring); a system menu (tap, then long press) with ≤ 10 custom items.
- Microphone: 16 kHz mono PCM (s16le); no speech-to-text for apps.
- Network: `fetch` and WebSocket to the origins listed in `app.json` (HTTPS in production); CORS as in any browser.
- Background: Android may suspend the WebView (sockets drop); no API to wake the display. **The only way to reach the owner while the app is closed is a phone notification, which the Even App mirrors to the glasses.**
- Distribution: a private build (`.ehpk`) sideloads without review. Anything packed into it can be extracted, so no API keys go in.

Prior art (14 projects surveyed) all use HTTP plus SSE or WebSocket from a bridge on the agent's machine. None aggregates Claude Code and Codex across machines with summaries. The closest is **Claude Remote** (`g2-claude-remote`), which reaches every `claude remote-control` session of an account through Anthropic's private Remote Control API.

## Decisions

1. **Own Even Hub app** (`muxtower-g2`), sideloaded. The official Even Terminal mode is a reference, not a target: one address and one agent type per connection, and its transcript-only UI cannot do summary-first reading.
2. **A hub ("tower")**: one muxtower daemon, the NAS, aggregates the others and is the only address the clients use. It is a star, not a distributed system (below).
3. **Voice** goes to the hub, which calls a cloud Whisper (Groq or OpenAI; keys only on the hub).
4. **Summaries** of long replies are made by the hub with a small LLM; the full text stays available.
5. **More session sources** behind one session model: tmux (today), Claude Code hooks installed globally (desktop-app and IDE sessions), Anthropic Remote Control (optional), Codex.

## System shape

```
MacBook ─ muxtowerd (spoke) ── outbound WSS ──┐
                                               ▼
NAS ───── muxtowerd (hub) ◄── Remote Control API (optional, the owner's Claude login)
          │  sessions from every source, summaries, ASR, push
          ▼  HTTPS via Cloudflare Tunnel → gate → Caddy
   web app (phone/desktop)      muxtower-g2 (Even App WebView → G2)
```

### Hub and spokes (star, single owner per session)

- Every daemon stays the **only owner** of its sessions: it detects state, sends keys, answers hooks. Nothing is replicated, so there is nothing to keep consistent.
- A spoke keeps one outbound WebSocket to the hub (no tunnel or open port on the MacBook; it reconnects across networks and sleep). Over it, the spoke pushes its session list and events, and the hub sends commands (approve, deny, input, resize) as request/response messages.
- The hub keeps a cached, merged view. Session ids become `<machine>/<id>`. A spoke that drops off shows its sessions as offline, with nothing lost.
- A spoke authenticates with a device token minted on the hub (`muxtower pair --spoke`), revocable like any device.
- Clients only talk to the hub. The web app can still add daemons directly. The hub is an option, not a requirement.

### Session sources (one session model, several adapters)

| source | finds sessions by | can show | can approve | can type replies |
|---|---|---|---|---|
| tmux (today) | scanning panes | screen, hooks if launched by muxtower | yes (menu + arrow keys) | yes |
| global Claude Code hooks (`muxtower hooks install`, opt-in, removable) | HTTP hooks from every Claude Code process on that machine: CLI, IDE, desktop app | state, tool calls, last reply, transcript file | yes: the `PermissionRequest` hook is held until the owner decides (falls back to the app's own prompt on timeout) | only if the session also runs in tmux |
| Anthropic Remote Control (optional, hub only) | the account's `claude remote-control` sessions on any machine; archived and dead ones are filtered by the API | events, archive state | yes | yes |
| Codex | its notify hook and session files | state, last reply | via tmux | via tmux |

Remote Control relies on private, reverse-engineered endpoints (`claude-rc-api`): they may change or break, and using them is at the owner's risk. It stays off by default and is isolated behind its own adapter.

**Verified 2026-10-18 (read-only listing with the owner's login, 174 sessions):**
- Sessions **started from the desktop app (`origin: desktop_app`) and the Android app are listed**, next to `claude remote-control` CLI sessions and Anthropic cloud sessions. `origin` is where a session was started; `environment_id` is the machine (a bridge) or `anthropic_cloud`. For example, sessions started in the desktop app but running on the NAS carry the NAS's environment.
- `status` is `active` or `archived`; `status_bucket` is `working`, `blocked`, `review_ready` or `completed`. `connection_status`, `worker_status` and `unread` are also present. Archiving is therefore known exactly.
- Machine names are **not** readable: the environment endpoints answer 404/405 to OAuth. The hub maps each `environment_id` to a name the owner gives once ("nas", "macbook"). Some older CLI sessions carry no environment id.
- `get_session` adds `post_turn_summary`: `{status_category, status_detail, recent_action, needs_action, is_noteworthy, …}`, Anthropic's own one-line summary of each turn. It also adds `task_summary` and `requires_action_details_list` (pending prompts). The glasses can use these directly for rows and pop-ups; the hub's own summaries are only needed for reading a long reply.

When a desktop-app session is archived, hooks alone may not say so. The hub uses `SessionEnd` and inactivity, and lets the owner dismiss a session. Remote Control sessions report archiving exactly.

### Voice

The glasses app records PCM while the owner holds a gesture, then uploads the utterance (WAV, ~32 KB/s) to `POST /v1/asr` on the hub. The hub sends it to the configured provider (Groq Whisper, OpenAI Whisper) and returns text. The glasses show the text, and a double tap sends it as input. Streaming recognition is a later option if a streaming provider is chosen.

### Summaries

When a session's reply exceeds what fits on a screen, the hub asks a small model (e.g. Claude Haiku) for a few short lines in the reply's language. These lines keep the decision points: questions asked, commands proposed, failures. The summary is cached with the reply. The glasses show the summary first; swiping opens the full text, paginated to the display. Summaries are made once per reply, not per viewer.

### Alerts

The hub owns notifications for all sources: Web Push to the owner's phone, mirrored to the glasses by the Even App. Optionally a second channel (ntfy or Telegram) where push mirroring is unreliable. Inside the open app, a session needing the owner moves to the top and can open itself.

## The glasses app (frontend template, adapted)

- `glasses/`: Vite + TypeScript + Even Hub SDK. The UI is SDK containers, not the DOM, so there is no React renderer. A screen is a plain description (`{title, text | list, footer, menu}`), and one renderer turns it into `textContainerUpgrade` (no flicker) or `rebuildPageContainer` (layout change). These screen primitives play the role of `components/ui/`. The display limits (characters, list items, 64-character labels) play the role of tokens and are enforced by a check, like colors in the web app.
- The phone panel is a small web page in the same app (settings: hub URL, pairing code, voice, notification preferences) and follows the web app's rules (tokens, shadcn-style primitives).
- State: `@tanstack/query-core` for server state, `zustand/vanilla` for UI state. The contract is the shared generated OpenAPI client (`packages/api-client`, also used by the web app).
- Screens: **Inbox** (sessions needing you first, labelled `@machine · agent`), **Session** (summary first, pending approval or question, full text on swipe), **Reply** (voice → text → confirm), plus a system menu (deny, quick replies, voice, refresh).
- Network: `app.json` lists the hub origin only. The device token is registered with the gate in front (gate `API_TOKENS`), so off-network requests pass.

## Glasses interaction design

Requirements from the owner's trial of Claude Remote (2026-10-18). Each one was a pain point there:

1. **Keep my place.** Going back to a list lands on the session I came from, not on the first row. Reopening the app lands where I left it.
2. **Sensible order that holds still.** Sessions needing me come first; nothing reorders while I am looking at a screen.
3. **Levels.** Not one flat list: a short home screen, then machines and agents, then sessions.
4. **Simple, consistent gestures**, and the owner can change them.
5. **Lists made for the glasses**: short rows, clear state, no scrolling hunt.

### Why not the SDK's list container

The SDK list has no "initially selected item": every rebuild selects row 1 (this is why Claude Remote, which uses it, forgets the position). It also holds at most 20 rows of 64 characters, and any change needs a full rebuild with a visible flicker. Instead, as claudedeck and glancecode do and as Even's own guidelines suggest (a `>` prefix as cursor), lists are **drawn in a text container with our own cursor**. Swipes move the cursor, and only the text is updated (`textContainerUpgrade`, no flicker). The window scrolls with the cursor, and rows are unlimited. To verify early in the simulator and on hardware: that every swipe reaches the app as an event when the text does not overflow.

### Screens and levels

```
Home                                Group: @nas                     Session: acme-api
> ! acme-api   @nas   approve       > acme-api      approve 2m     BASH  npm run db:migrate
  ! docs-site  @mac   question        billing       working        > Yes
  ─────                               web           idle 1h          Yes, don't ask for npm run *
  @nas        5 · 1 needs you                                        No
  @macbook    3 · 1 needs you                                      ─────
  codex       1                                                    Summary: …  (swipe for full)
```

- **Home** shows what needs me inline, oldest wait first, then one row per group (machine or agent) with counts. Groups and their order come from the hub, and the owner can reorder them.
- **Group** shows its sessions: pinned first, then by last activity.
- **Session** shows the pending approval or question first, if any; then the summary of the last reply. Swiping down pages through the full reply.
- **Reply**: hold to talk, then the text, then confirm.

### Order and memory rules

- The cursor follows a **session id**, not a row number: when rows change, it stays on the same session.
- While a screen is visible, rows do not move. New or changed sessions get a `•` marker, and the order is refreshed when the screen is entered again. One exception: a new "needs you" session is announced in the footer.
- Each screen remembers its cursor. Going back restores it, and it is stored on the device (`setLocalStorage`) so a relaunch restores it too.
- On launch: if exactly one session needs me, open it; otherwise show Home with the cursor on the session I last opened.

### Gestures (defaults, remappable)

| gesture | lists | session | reply |
|---|---|---|---|
| swipe up / down | move cursor | move between choices, then page the reply | — |
| tap | open | choose; a second tap confirms an approval | send |
| double tap | back one level | back | cancel |
| long press | — | hold to talk (voice reply) | re-record |
| tap, then long press | system menu: quick replies, deny, refresh, settings | same | — |

Approvals always take two taps (choose, confirm), so a stray touch never approves anything.

### Language

- The app's own labels stay English (project rule), but the content is whatever the agents and the owner write, very often Chinese. Claude Remote's voice input is English-only, which made it unusable for the owner.
- The firmware's single font covers Latin and CJK. Glyphs it lacks are dropped silently (no placeholder), so the renderer maps emoji and other unsupported symbols to text before drawing.
- Line breaking and the screen budget count CJK characters as double width. A screen holds far fewer Chinese characters than Latin ones, so summaries get a budget per script.
- Voice: the language is auto-detected or pinned per device (`zh`, `en`, mixed). Mixed Chinese and English in one sentence is the normal case to optimize for. Whisper (Groq) and gpt-4o-transcribe (OpenAI) are both candidates; the choice is a trade-off for later.
- Summaries are written in the language of the reply.

### Screen on and off (inside the app)

The SDK cannot switch the display or set global brightness; those are system-menu items. What the app can do, and uses:
- A blank page (or text brightness 0) reads as "off".
- Head pose (`imuControl`): look up to wake, look down to blank.
- `isWearing`: stop drawing when the glasses are off.
- Foreground events: know when the system menu or another layer covers the app.

Default behavior: blank until something needs the owner or the owner looks up, then show it, and blank again after a timeout. Staying resident (Android WebView suspension), battery use and notification overlap are deferred: the owner's sessions are short.

### Beyond agents: cards

The app is meant to become the owner's home screen on the glasses, instead of the firmware dashboard. The home screen is a list of **cards**. Each card is a hub-side module that provides a one-line status, a detail screen and actions:
- **Agents**: the core; part of muxtower.
- **Owner-only cards** such as calendar, Home Assistant, weather, and "ask AI" (voice → hub → Claude → summary) live as private plugins outside the open-source core.

### Settings the owner controls (phone panel, stored on the hub per device)

Gesture map, quick replies, pinned and hidden sessions, group order, sort of the "needs you" list (oldest first or newest first), and whether summaries are shown first. They are stored on the hub, so the web app can edit them too, and a reinstall keeps them.

## The daemon side (backend template)

New domain folders, each with routes / service / port / adapter: `federation/` (spoke uplink and hub registry), `sources/` (tmux, global hooks, Remote Control, Codex adapters behind one port), `asr/` (provider port: Groq, OpenAI), `summaries/` (model port; cache), `notify/` (extra channels). The existing sessions, approval and auth code stays as it is.

## The auth template

Not applicable: no user accounts. One owner per hub; phones, glasses and spokes are devices with revocable tokens.

## Open questions (next discussion)

1. Hub transport for spokes: WebSocket with request/response framing, or the spoke exposing its own API to the hub through a reverse tunnel?
2. Remote Control: worth the private-API risk, or rely on global hooks plus tmux and accept that replies need tmux?
3. Summaries: which model and provider, what length budget per screen, and should short replies skip them?
4. Codex: notify hook plus session files, or its app-server protocol?
5. Gate: register device tokens in gate, or put the hub's host in gate's observe mode?

# muxtower design

muxtower lets coding agents running in tmux on a remote machine (and, optionally, Claude Code Remote Control sessions anywhere) be approved and driven from a phone. It is server-side and headless: `muxtower serve` runs next to the agents, exposes a typed HTTP + WebSocket API behind a single Bearer token, and is meant to sit behind any reverse proxy. The web app is a client of that API, nothing more.

## Pieces

| piece | what | ships as |
|---|---|---|
| `muxtower` | the one command. `muxtower serve` runs the daemon (session registry, state detection, approvals, push, API); `muxtower` (status), `run`, `attach`, `pair` manage it locally through a 0600 CLI token; `run` starts the daemon in the background if it is not running. Five commands, nothing more | console script in the `muxtower` Python package |
| `muxtower-app` | PWA client (Vite + React); talks to one or many daemons | built into the wheel and served by `muxtower serve` at `/`; also a standalone static build / container |

`pipx install muxtower` gives a working daemon **and** UI. The bundled UI is the recommended way to use it (same origin as the API, no CORS, works on plain-HTTP LANs). A separately hosted app is supported for people who want one UI across several daemons.

## Sessions

- A session is one agent process in its own tmux session on a dedicated socket (`-L muxtower`), started by `muxtower run <agent> [args]` or `POST /v1/sessions`. Only binaries from the runtime registry may be launched; the API never takes a shell string.
- The launcher sets `MUXTOWER_SESSION_ID` and a per-session `MUXTOWER_HOOK_TOKEN` in the tmux environment, so hooks fired by the agent can be tied back to the session.
- Other **session sources** list sessions muxtower did not start and does not reach through tmux. Today there is one, optional (`[remote_control] enabled`): Claude Code Remote Control, Anthropic's controller API for the Claude account logged in on the daemon's machine (`muxtower.vendor.claude_rc`, a private API wrapped behind one port so a break is fixed in one module). It sees sessions started from the desktop app, the mobile apps and `claude remote-control`, on any machine (`machine` maps the opaque `environment_id` to a name from config; `origin` is where it was started).
- `SessionDirectory` is the single place that knows which source a session lives in. Routes and the stream ask it; it checks the session's `capabilities` (`screen`, `conversation`, `keys`, `resize`, `terminate`, `rename`) and answers 409 for anything a source cannot do, instead of sending keys to the wrong place. Clients choose their view from the same flags: a terminal for `screen`, the structured conversation for `conversation`.
- A Remote Control session has no screen. Its state comes from the worker's own status and the unanswered permission prompt in its event log; its conversation (`GET /v1/sessions/{id}/conversation`, stream topic `conversation`) is built from the log as typed items (prompt, reply, tool, approval, question, result) that are re-sent with the same `seq` when their status changes; Anthropic's per-turn summary becomes `Session.summary`. A poll lists active sessions every few seconds and fetches events only for sessions whose fingerprint changed; answering re-reads the log first. Approve, deny, messages and interrupt (`Escape`) go back through the same API.
- Registry, device tokens, push subscriptions and the audit log live in one SQLite file under `$XDG_STATE_HOME/muxtower/` (default `~/.local/state/muxtower/`). Config lives in `$XDG_CONFIG_HOME/muxtower/config.toml`, every key overridable by a `MUXTOWER_*` env var.

## State detection: runtime adapters

Each agent runtime is an adapter implementing one port:

```
detect(session) -> State            # current coarse state
pending(session) -> PendingAction?  # what is being asked, if anything
approve(session, option) / deny(session)
```

Sources, in priority order:

1. **Structured events (primary).** For Claude Code, the launcher passes `--settings` with `type: "http"` hooks pointing at `POST /v1/hooks/claude-code` (header `Authorization: Bearer ${MUXTOWER_HOOK_TOKEN}`, `allowedEnvVars` set). Nothing is written into the user's own `settings.json`. Events used:
   - `PermissionRequest` → state `needs_permission`, with `tool_name` / `tool_input` / `permission_rule` shown on the phone. The daemon answers immediately with an empty body (v0.1: report only, the dialog still appears in the terminal and is answered by keystroke). Holding the request open and answering `allow`/`deny` from the phone is a later, opt-in mode.
   - `Notification` (`permission_prompt`, `idle_prompt`, `elicitation_dialog`, `agent_needs_input`) → needs-attention states.
   - `PreToolUse` / `PostToolUse` → `busy`; `Stop` → `idle` + `last_assistant_message` (replaces scraping the reply off the screen); `SessionStart` / `SessionEnd` → lifecycle.
2. **Screen rules (fallback / custom).** A capture loop classifies every pane with an ordered rule list loaded from TOML (`runtimes/defaults/<name>.toml`, replaced file-by-file by `$XDG_CONFIG_HOME/muxtower/runtimes/<name>.toml`). Rules are data, not code: a regex and the state it means. A `[menu]` section names the cursor glyph; the menu parser reads the block of choices around it (numbered or not, wrapped labels joined). Used for runtimes without hooks, adopted panes, and as the cross-check that clears a stale hook state. The session view exposes `matched_rule`.

Approval is always explicit. Approve re-reads the live screen, parses the menu, picks the requested option (or the runtime's `[approve.prefer]` choice, exposed as `pending.recommended`), and moves there with arrow keys before Enter. It never types digits, so a stray key cannot land in the next dialog. It refuses (409) when no dialog is on screen; a hook-only dialog is acted on only after it has had a second to render and its menu is readable. Auto-approve is a per-session switch, limited to the runtime's `auto_approve_states`, and acts only on dialogs the screen rules recognise.

## API

- Versioned under `/v1`. FastAPI's OpenAPI schema is exported to `openapi.json` at the repo root and is the contract for the app (`openapi-typescript` + `openapi-fetch`); CI fails if it is stale.
- One WebSocket, `/v1/stream`: the client sends `{"type":"subscribe","topic":"sessions"}`, `{"type":"subscribe","topic":"screen","session_id":…,"history":N}` or `{"type":"subscribe","topic":"conversation","session_id":…}`; the server pushes `sessions`, `screen` and `conversation` frames (shapes in the OpenAPI schema via `/v1/stream/schema`).
- Health: `GET /v1/health` is public and returns only `{status, version}`.

## Auth

- **No accounts.** A daemon has one owner; the app keeps its daemon list (URL + token) only in the browser that added it. There is no server-side user store anywhere.
- **Device tokens.** Every paired device gets its own named token, stored hashed on the daemon, so a lost phone is revoked alone (from the app's daemon page, or `muxtower pair --revoke <name>`).
- **Transport.** HTTP: `Authorization: Bearer`. WebSocket (browsers cannot set headers): when the app is served by the daemon itself, an HttpOnly, SameSite=Strict cookie scoped to `/v1/stream` (minted by `POST /v1/stream/cookie`, accepted only with a same-origin `Origin`, never read by REST routes). Otherwise the app offers the token as a subprotocol, `Sec-WebSocket-Protocol: muxtower, bearer.<token>`, which keeps it out of URLs and logs; if that handshake is refused, it retries once with `?access_token=` and remembers that for the daemon (never `?token=`: password/token gates count an unknown `token` parameter as a guess). Before any handshake one `GET /v1/me` must succeed: a 401 carrying `X-Muxtower-Auth` (sent by the daemon on every 401 of its own) means the token was revoked; any other 401/403 means a gate in front refused, and the app shows a sign-in prompt and retries once a minute without sockets. The daemon redacts `access_token=` from access logs.
- **Pairing = one-time codes.** A device never receives a token by being shown it. Instead a short-lived (5 min), single-use pairing code is shown as a QR for `<app-url>/pair#u=<daemon-url>&c=<code>` (the fragment never reaches a server), and the new device redeems it at `POST /v1/pair/claim` for its own fresh token. Two ways to get a code:
  - `muxtower pair` on the daemon's machine (first device). The daemon cannot know which address a device will use, so without `--url`/`public_url` it prints only the code (plus the addresses it can see, as hints) and the device enters it on whatever address it opened: the bundled UI pairs with its own origin (`/pair#c=<code>` or the inline code field). With a known address it also shows a QR code;
  - **from an already-paired device**: the app's "Add another device" shows one QR carrying a fresh code for every daemon it knows, so a phone that is paired once can pair a laptop in one scan. A photographed QR is useless once redeemed or expired.
- **Shared mode.** `pairing.mode = "shared"` makes claims hand out one existing named token instead, for setups where a front gate must already know every token it lets through.
- **Public URL.** `public_url` in config is what pairing and the bundled `/config.json` advertise; behind a proxy the daemon never guesses its own address from the request.

## CORS and origins

- Default `cors.allowed_origins = ["*"]`. This is safe because auth is bearer-only: no cookies are ever sent, so a foreign page can call nothing but `/v1/health` and `/v1/pair/claim` without a token. Listing origins only tightens it. `allow_credentials` is false; allowed headers are `Authorization`, `Content-Type` and whatever `cors.extra_headers` lists (a gate's own credential header, for apps that run off the daemon's origin); preflights are cached 10 minutes.
- Browsers do not apply CORS to WebSockets; `/v1/stream` checks `Origin` against the same list (any origin by default) and always requires the token.
- A reverse proxy or gate in front must let `OPTIONS` preflights through untouched, since they carry no credentials.
- The app never goes through a proxy of its own: a hosted app talks to daemons directly from the browser, so the host never sees tokens or terminal contents.

## HTTPS

HTTPS is the expected setup, not an extra: service workers, installing the PWA and Web Push only work in a secure context (localhost excepted). `muxtower serve` binds `127.0.0.1` by default and warns when it binds anything else while `public_url` is not `https://`. Documented ways to put HTTPS in front:

1. **Tailscale** (personal use): `tailscale serve --bg 8731` → `https://<machine>.<tailnet>.ts.net`, certificate managed by Tailscale, no domain or open port.
2. **Cloudflare Tunnel**: a public hostname, no open port, TLS at Cloudflare.
3. **Caddy** (own domain): `reverse_proxy 127.0.0.1:8731`, certificates issued automatically.

A hosted HTTPS app cannot reach a plain-HTTP or private-IP daemon (mixed content, Local Network Access); such daemons use their bundled UI.

## Hosting the app

The app is a static SPA; the same build runs anywhere.

- **Bundled** (recommended): served by `muxtower serve` at `/`, same origin as its daemon. The glasses app (`glasses/`) is bundled next to it at `/g2/`.
- **Your own static host**: one-click "Deploy to Cloudflare" (Workers static assets, SPA fallback via `not_found_handling`) or fork + GitHub Pages (Actions workflow; base path from `MUXTOWER_BASE`). Add daemons by pairing.
- **A public instance** run by the project, for convenience only. It is built and deployed by public CI from tagged releases, so users can check what they run; the docs still recommend the bundled UI, because whoever serves the JS could read the tokens in that browser.

## One entry per agent

A Claude Code process can be both a tmux pane and a Remote Control session. The process writes `~/.claude/sessions/<pid>.json`, whose `bridgeSessionId` (`session_<id>`) is its Remote Control session (`cse_<id>`). The capture loop looks for that file from each pane's process down (the pane may run a shell first); the directory then lists the agent once, under its tmux id, with the remote side's name, origin, summary and conversation. Text messages to such an agent go through Remote Control (structured, cannot land in a dialog); keys go to tmux.

## The concierge (optional)

`[concierge] enabled` keeps one Claude Code session running on the daemon's machine for the owner to talk to instead of each session: it relays the owner's requests, reads and summarizes sessions, answers their prompts when the owner says so, starts new ones, and also answers ordinary questions. It is launched by muxtower in tmux (`--model sonnet`, its own instructions, Remote Control on by default so the Claude apps reach it too) with an MCP config that points at `/v1/mcp` with a token minted for it.

- Tools: `list_sessions`, `read_session`, `send_message`, `approve`, `deny`, `interrupt`, `start_session`, `watch_session`, `unwatch_session`. Plain-text results, short enough to relay.
- Watching: when a watched session finishes a turn or starts needing the owner, muxtower types a one-line `[muxtower] …` message into the concierge (held while the concierge itself shows a prompt, so the text cannot answer it).
- Its instructions say that only the owner's messages are instructions; what it reads from sessions is data.
- Clients pin it (`role: "concierge"`); on the glasses, talking outside a session talks to it.

## Reply summaries and voice

- **Summaries.** A reply longer than `summaries.min_chars` gets a few lines in its own language that keep what the owner must decide, commands proposed and failures. They are made by a coding agent CLI already logged in on the daemon's machine (`claude -p` with haiku, or `codex exec`), so a subscription is used instead of an API key. The CLI runs with no tools, settings or MCP servers in an empty directory, and gets the reply on stdin. Each reply is summarized once (keyed by its hash, cached in SQLite), in the background: when a client asks (`POST /v1/sessions/{id}/summary`) and, with `summaries.eager`, as soon as a session starts needing the owner. Sessions carry it as `reply_summary`; the stream pushes the list again when one is ready.
- **Voice.** `POST /v1/asr` takes a recording (WAV from the glasses) and returns text through an OpenAI-compatible transcription API (Groq `whisper-large-v3-turbo`, OpenAI `gpt-4o-transcribe`). The key stays on the daemon; nothing is stored, and the audit log records only sizes. Each request carries a prompt written in Simplified Chinese with the current session names and common terms: Whisper follows the prompt's script (no Traditional characters for Mandarin) and spells those names right. The client shows the text and sends it only after the owner confirms.
- `GET /v1/me` lists which of these the daemon offers (`features`).

## Read state and hidden sessions

With many sessions running, the owner needs to see which finished turns they have not looked at yet: those are what to pick up next. The daemon keeps, per session, when it last finished a turn (`sessions/turns.py`) and when anyone last looked at it (`sessions/marks.py`, table `session_marks`), so every device agrees. A session is `unread` when it finished after the last look, when its source's own flag says so for activity since then (Remote Control's unread, shared with the Claude apps), or when the owner marked it unread to come back to. `POST /v1/sessions/{id}/read` (`{"read": false}` marks unread) is sent by a client when it opens a session, when an open session gets news, and every 30 s while it stays on screen; reading also marks the session read on Remote Control. A session looked at in the last 45 s gets no "done" notification: someone is watching it. The same store keeps which sessions the owner **hid** (`POST /v1/sessions/{id}/hide`): they leave every list and count, show only under "Hidden", and send no "done" notifications (a hidden session that gets blocked still alerts). Hiding keeps the agent running; **archiving** ends it (`POST /v1/sessions/{id}/archive`, after the owner confirms): its tmux pane closes (muxtower's own tmux session, for one it started), a Remote Control session is archived there too (first, so a failure changes nothing), and the session is kept to read under "Archived" (`sessions/archive.py`, table `archived_sessions`): its last view, and its conversation from the Claude Code transcript (the file outlives the process) or, without one, the items it had. An archived session is read-only (no screen, no input, no read state); `DELETE` deletes it from the archive. In the list, a resting unread session is its own status, "Finished, unread", between "Needs you" and "Working" (a check in the accent color, bold name); the list menu marks everything shown read, the session menu marks one unread.

## Push

Web Push with a per-daemon VAPID key. A browser registration holds one subscription, so the app registers its service worker once per daemon (scope `<base>push/<daemonId>/`, same script). The subscription belongs to the app's origin; the notification payload carries `daemon_id` and `session_id`, and a click opens `/d/<daemon>/s/<session>`. Filters per subscription: which states notify, whether finished turns do (`done`, on by default), muted sessions. A subscription belongs to the paired device that registered it: once that device is revoked, the daemon drops it at the next push instead of sending. The app registers its subscription again on every start, which keeps the daemon's copy current and ties older ones to their device. Registering a fresh worker waits for that registration's own worker to activate (`navigator.serviceWorker.ready` is the page's root registration).

Two kinds of notification, both one per session (a newer one replaces the older, so a handled approval gives way to "Done"):

- **attention** — a session entered a state that needs the owner. Stays on screen until dismissed.
- **done** — a session finished a turn: `sessions/turns.py` sees it busy for at least 5 s, then idle for 6 s (a screen read can flicker; a pause to ask is covered by the attention alert, and sessions seen at startup are only learned). Not sent for the assistant, whose replies are the conversation itself.

The text (`notify/text.py`): the title is the session's name, like a message's sender; the body starts with what is wanted or what happened — "Approve Bash: npm run build", "Question: …", "Plan ready for review", "Error: …", "Done: <what it did>", or "Done, waiting for you: <what it left>" from Remote Control's turn summary — then where it runs ("nas · ~/projects/web"). Markdown is flattened to one line.

## App

- Vite + React + TypeScript PWA; Tailwind v4 tokens; shadcn/ui primitives; TanStack Router, TanStack Query, Zustand.
- Terminal view: the pane's screen plus scrollback, converted from ANSI to HTML lines and shown as selectable text in a natively (pixel-) scrolling box. Scrolling never touches tmux. Each snapshot is aligned with what is shown (lines pushed off the top, older lines added on top) and only changed lines are patched, keeping the reader's place. Nearing the top asks the stream for more history (300 → 1500 → 5000 lines). "Fit width to this screen" resizes the pane to the view, as wide as it and "Height" screens of it tall (1–4×, default 2×: a full-screen program keeps no scrollback, so a taller pane is what lets it show more than one screen; the view scrolls through it) (default for sessions muxtower started and for panes no terminal is attached to — `terminal_attached` on the session; a pane someone has open in a terminal keeps that terminal's size until asked; in a split window the window grows by the other panes' room and the pane is set exactly); turning it off, leaving, or closing the page calls `POST /v1/sessions/{id}/resize/release`, which unsets tmux's manual `window-size` and runs `resize-window -A`, so attached terminals get their size back.
- Daemons are first class: a persisted list `{id, name, url, token}`; one typed client per daemon; every query key starts with the daemon id.
- Sessions are classified four ways, everywhere the same: **status** (needs you, error, finished and unread, working, idle), **device** (the machine, as its daemon names it; a Remote Control session running on no daemon's machine is named by the kind of machine its folder is on — `/Users/…` is a Mac — or else "No environment": the Claude desktop app, for one, names no machine for its sessions and its log often no folder; the owner places such a session by hand (`PUT /v1/sessions/{id}/placement`: a device and a folder, kept with their marks and over what the source says) or asks for its whole log to be read for the folder its tool calls ran in (`POST …/placement/detect`, on request only: the daemon keeps just the end of each log), never guessed from tool output), **folder** (where the agent works, home shown as `~`: the folder Claude started in, or the deeper one its tools run in, read from the Remote Control log; for sessions on no daemon's machine only the log says) and **source** (muxtower, tmux, or how Claude Code was started: for a process on a daemon's machine, the `entrypoint` its process file states (`cli`, `sdk-cli`, an IDE…); for one elsewhere, the session's `remote-control-*` tag — `sdk` is the desktop app, which runs Claude Code through the SDK — since Remote Control's listing says CLI for every session).
- Screens: **Sessions** — one list of every session on every daemon, narrowed to a view (all, needs you, unread, working), a device or one of its folders, or a source, grouped by status (default), by device and then folder (a two-level list: sticky device headers, folder sections), or by source, searchable; every group header (a device, a folder, a status) folds what is under it, remembered per grouping on this device, still counting what it holds and how many of those need you, and a search shows everything; rows leave out what their group already says, and slide to their new place when they change groups; a session opened from the list that then leaves it (opening an unread one reads it) stays at the bottom under "Just opened" until the list shows something else, so a mistaken tap is easy to see and undo; what needs you comes first with one-tap approval where there is a usual choice; the assistant is pinned on top. **Session** — header (name, state, device · folder · source, a "⋯" menu for terminal settings, rename, auto-approve, stop), the prompt waiting for an answer, the terminal or the conversation (a switch when both exist; replies are rendered Markdown — CJK-friendly emphasis — raw HTML shown as text; a run of tool calls is one line that opens to the calls: a single call's own description, else counts by kind such as "Ran 4 commands, read 2 files", failures counted apart), the input bar (one row: a "+" that opens the keys a phone lacks above it — esc, tab, ⇧tab, ^C, backspace, space on the left, arrows as an inverted T and a tall Enter on the right, arrows and backspace repeating while held — the message box, Send; what is typed is kept per session on this device until it is sent, through switching sessions or the phone closing the app). The New session dialog suggests the folders the daemon's sessions already use. Every row has the session's actions (mark read or unread, rename, hide or show, stop; rename and stop where its capabilities allow): swipe right on a touch screen, or the "⋯" that appears on hover with a mouse; the session page's menu has the same ones. **Daemons** — add by pairing link/QR or by hand, per-daemon push settings, and what this browser can do to put the app on the home screen: a one-tap Install where the browser offers it (Chrome installs a real app, whose notifications carry its name and icon), the way through Chrome's own menu while Chrome has not offered yet, the Share › Add to Home Screen steps on iPhone (needed there for push), and, in Android browsers that only add shortcuts, the way to Chrome (pair it with Add another device › Copy link); nothing when it already runs installed.
- History of full-screen agents: Claude Code with `tui: fullscreen` draws on the terminal's alternate screen, so tmux keeps no scrollback and the terminal view can only show the visible screen. Every tmux session whose Claude Code writes a transcript (`~/.claude/projects/<cwd as dashes>/<sessionId>.jsonl`, found through its process file) has a conversation read from that file (`sessions/transcripts.py`: its last 3 MB at first, then followed every 1.5 s and pushed on the stream), also when it runs Remote Control, since the transcript holds the whole history. Sessions report `alt_screen`; their terminal view shows a bar that switches to the conversation.
- Layout follows the width: phones show one pane at a time with bottom tabs; from `md` the list and the session sit side by side; from `lg` a sidebar adds the views, each device with its folders (foldable), and the sources, with their counts. The list's view, scope, grouping and search live in the URL; going back lands on the same list at the same scroll position.
- Terminal cells: non-ASCII characters get exactly the cells tmux counts (wide characters a centered two-cell box), so the grid holds whatever font a device falls back to. Fit measures one line of the real font and line height; when lines overflow and fit is off, the view offers "Fit width".
- No configuration is baked into the bundle. An optional `/config.json` (`{"daemons": [{name, url, token?}], "acknowledge_public_tokens"?}`) next to `index.html` supplies default daemons, written at build time from `MUXTOWER_APP_CONFIG`; a preset token requires the acknowledgement and shows a warning. The bundled copy served by the daemon advertises its own daemon.

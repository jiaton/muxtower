# muxtower design

muxtower lets coding agents running in tmux on a remote machine (and, optionally, Claude Code Remote Control sessions anywhere) be approved and driven from a phone. It is server-side and headless: `muxtower serve` runs next to the agents, exposes a typed HTTP + WebSocket API behind a single Bearer token, and is meant to sit behind any reverse proxy. The web app is a client of that API, nothing more.

## Pieces

| piece | what | ships as |
|---|---|---|
| `muxtower` | the one command. `muxtower serve` runs the daemon (session registry, state detection, approvals, push, API); `muxtower` (status), `run`, `attach`, `pair` manage it locally through a 0600 CLI token; `run` starts the daemon in the background if it is not running. Five commands, nothing more | console script in the `muxtower` Python package |
| `muxtower-app` | PWA client (Vite + React); talks to one or many daemons | built into the wheel and served by `muxtower serve` at `/`; also a standalone static build / container |

`pipx install muxtower` gives a working daemon **and** UI. The bundled UI is the recommended way to use it (same origin as the API, no CORS, works on plain-HTTP LANs). A separately hosted app is supported for people who want one UI across several daemons.

## Sessions

- A session is one agent process in its own tmux session on a dedicated socket (`-L muxtower`), started by `muxtower run <agent> [args]` or `POST /v1/sessions`. Only binaries from the runtime registry may be launched; the API never takes a shell string.
- The launcher sets `MUXTOWER_SESSION_ID` and a per-session `MUXTOWER_HOOK_TOKEN` in the tmux environment, so hooks fired by the agent can be tied back to the session.
- Panes are captured every `tick_seconds` (1 s), except one whose window tmux says had no output since before its last capture (`window_activity`, in whole seconds) and that nobody watches, which is read again only every 5 s; and soon after input is sent to a session or a hook reports on one, so what was typed shows at once: keys typed in a row are captured together (after 40 ms), and captures stay at least 100 ms apart however often something asks.
- Other **session sources** list sessions muxtower did not start and does not reach through tmux. Today there is one, optional (`[remote_control] enabled`): Claude Code Remote Control, Anthropic's controller API for the Claude account logged in on the daemon's machine (`muxtower.vendor.claude_rc`, a private API wrapped behind one port so a break is fixed in one module). It sees sessions started from the desktop app, the mobile apps and `claude remote-control`, on any machine (`machine` maps the opaque `environment_id` to a name from config; `origin` is where it was started).
- `SessionDirectory` is the single place that knows which source a session lives in. Routes and the stream ask it; it checks the session's `capabilities` (`screen`, `conversation`, `keys`, `resize`, `terminate`, `rename`) and answers 409 for anything a source cannot do, instead of sending keys to the wrong place. Clients choose their view from the same flags: a terminal for `screen`, the structured conversation for `conversation`.
- A Remote Control session has no screen. Its state comes from the worker's own status and the unanswered permission prompt in its event log; its conversation (`GET /v1/sessions/{id}/conversation`, stream topic `conversation`) is built from the log as typed items (prompt, reply, tool, approval, question, result) that are re-sent with the same `seq` when their status changes; Anthropic's per-turn summary becomes `Session.summary`. A poll lists active sessions every few seconds and fetches events only for sessions whose fingerprint changed; answering re-reads the log first. Approve, deny, messages and interrupt (`Escape`) go back through the same API.
- Registry, device tokens, push subscriptions and the audit log live in one SQLite file under `$XDG_STATE_HOME/muxtower/` (default `~/.local/state/muxtower/`). Config lives in `$XDG_CONFIG_HOME/muxtower/config.toml`, every key overridable by a `MUXTOWER_*` env var.

## State detection: runtime adapters

Each agent runtime is an adapter implementing one port:

```
detect(session) -> State            # current coarse state
pending(session) -> PendingAction?  # what is being asked, if anything
approve(session, option) / deny(session)
```

Sources, in priority order:

1. **Structured events (primary).** Hooks of the agent's harness, for the sessions muxtower starts: a runtime names its harness (`hooks = "claude-code"`, `"codex"`), and the harness (`hooks/ports.py` `HookHarness`, one module each, listed in `hooks/harnesses.py`) says how its agent is told to report without touching the owner's own config (`launch_args`) and how to read what it reports (`event`). Every harness muxtower knows names its events the way Claude Code does, so that is the one vocabulary (`hooks/events.py`), turned into state the same way; a harness adds only which tool calls are the agent asking the owner (Claude Code's `AskUserQuestion`, `ExitPlanMode`). Events arrive at `POST /v1/hooks/<harness>` with the session's id and its token (only the token's hash is kept). A new harness with Claude-style hooks is one module.
   - **Claude Code**: the launcher passes `--settings` with `type: "http"` hooks pointing at `/v1/hooks/claude-code` (header `Authorization: Bearer ${MUXTOWER_HOOK_TOKEN}`, `allowedEnvVars` set). Nothing is written into the user's own `settings.json`.
   - **Codex** (checked against 0.164 and 0.165; its hooks have no http type): `-c hooks={…}` adds a command hook per event that runs `hooks/relay.py` with the daemon's Python (`-I -S`, standard library only, about 20 ms), which posts the event Codex hands it on stdin and waits for the answer, so events arrive in order. It reads where to post and the token from a 0600 file of the session's (`<state>/hooks/<id>.codex.json`), since Codex starts hooks with an environment it filters. Codex runs a hook someone added only once it is trusted, keyed by where it is declared and a hash of what it runs; trust given on the command line counts (`hooks.state`), so muxtower trusts exactly the hooks it adds, for the session it starts, computing Codex's hash (SHA-256 of the sorted JSON of the normalized hook, timeouts at 3 s, the most Codex allows some events), and writes nothing into `~/.codex`. Should a Codex version hash differently, the session asks "Hooks need review" at startup (a screen rule; approving continues without trusting) and nothing runs untrusted. Codex starts such a session in its own process rather than its shared background server (it does so for any `-c`).
   - Events used:
   - `PermissionRequest` → state `needs_permission`, with `tool_name` / `tool_input` / `permission_rule` shown on the phone. The daemon answers immediately with an empty body (v0.1: report only, the dialog still appears in the terminal and is answered by keystroke). Holding the request open and answering `allow`/`deny` from the phone is a later, opt-in mode.
   - `Notification` (`permission_prompt`, `idle_prompt`, `elicitation_dialog`, `agent_needs_input`) → needs-attention states (Claude Code only).
   - `PreToolUse` / `PostToolUse` → `busy`; `Stop` → `idle` + `last_assistant_message` (replaces scraping the reply off the screen); `Interrupt` (Codex) → `idle`; `SessionStart` / `SessionEnd` → lifecycle.
2. **Screen rules (fallback / custom).** A capture loop classifies every pane with an ordered rule list loaded from TOML (`runtimes/defaults/<name>.toml`, replaced file-by-file by `$XDG_CONFIG_HOME/muxtower/runtimes/<name>.toml`). Rules are data, not code: a regex and the state it means, optionally searched in the screen's last lines only (`last_lines`) for a sign that sits at the bottom, so an answer quoting it does not count (Claude Code's "working" is its spinner line or its status bar's hint, Codex's its status line). A `[menu]` section names the cursor glyph; the menu parser reads the block of choices around it (numbered or not, wrapped labels joined). Used for runtimes without hooks, adopted panes, and as the cross-check that clears a stale hook state. The session view exposes `matched_rule`. Rules run on every pane every second, over the whole screen (DOTALL) unless `last_lines` narrows it, so each must be linear: a pattern opening with a lookahead is refused at load (anchor it, `\A(?=…)`; unanchored, it is tried at every position and each try scans to the end), and a test times every default rule on a 20 000-character screen. A runtime may name its input box (`prompt`): while the box shows at the bottom, the rules for a dialog see only the panel framed right above it (`panel_rule`: Claude Code's tips sit there), or nothing, so a dialog's words quoted in a reply or a diff make no dialog (the app would offer Deny, which is Escape, and interrupt a session at work); dialog rules also look only at the bottom (`last_lines`), a footer as the last line. An error counts only as the last thing the agent said: Claude Code's `api-error` sees only what is above the input box (`above_prompt`), its own ● line followed at most by the turn's ✻ done line, so an older error scrolled up, or one quoted in a message, is none; and a hook well after a screen's error (`ERROR_GRACE_SECONDS`) says the agent went on. And a hook since that screen showed (working, done) beats the screen's dialog, as does any hook at all a screen's trust dialog (they come at startup, before hooks): hooks report the agent's own prompts.

Approval is always explicit. Approve re-reads the live screen, parses the menu, picks the requested option (or the runtime's `[approve.prefer]` choice, exposed as `pending.recommended`), and moves there with arrow keys before Enter. It never types digits, so a stray key cannot land in the next dialog. It refuses (409) when no dialog is on screen; a hook-only dialog is acted on only after it has had a second to render and its menu is readable. Auto-approve is a per-session switch, limited to the runtime's `auto_approve_states`, and acts only on dialogs the screen rules recognise.

## API

- Versioned under `/v1`. FastAPI's OpenAPI schema is exported to `openapi.json` at the repo root and is the contract for the app (`openapi-typescript` + `openapi-fetch`); CI fails if it is stale.
- One WebSocket, `/v1/stream`: the client sends `{"type":"subscribe","topic":"sessions"}`, `{"type":"subscribe","topic":"screen","session_id":…,"history":N}` or `{"type":"subscribe","topic":"conversation","session_id":…}`; the server pushes `sessions`, `screen` and `conversation` frames (shapes in the OpenAPI schema via `/v1/stream/schema`). `{"type":"ping"}` is answered with a `pong` frame: the app asks after 25 s without any frame and takes a connection that does not answer within 5 s for dead (a phone that changed networks keeps an `open` socket nothing arrives on), dropping it and connecting again at once. It also connects at once, instead of at the end of its backoff (1 s doubling to 15 s), when the page is shown again or the network comes back, and asks an open connection then. A session's header shows a small dot: live, polling (the connection is down, queries poll), or offline.
- Health: `GET /v1/health` is public and returns only `{status, version}`.

## Auth

- **No accounts.** A daemon has one owner; the app keeps its daemon list (URL + token) only in the browser that added it. There is no server-side user store anywhere.
- **Device tokens.** Every paired device gets its own named token, stored hashed on the daemon, so a lost phone is revoked alone (from the app's daemon page, or `muxtower pair --revoke <name>`).
- **Transport.** HTTP: `Authorization: Bearer`. WebSocket (browsers cannot set headers): when the app is served by the daemon itself, an HttpOnly, SameSite=Strict cookie scoped to `/v1/stream` (minted by `POST /v1/stream/cookie`, accepted only with a same-origin `Origin`, never read by REST routes). Otherwise the app offers the token as a subprotocol, `Sec-WebSocket-Protocol: muxtower, bearer.<token>`, which keeps it out of URLs and logs; if that handshake is refused, it retries once with `?access_token=` and remembers that for the daemon (never `?token=`: password/token gates count an unknown `token` parameter as a guess). Before any handshake one `GET /v1/me` must succeed: a 401 carrying `X-Muxtower-Auth` (sent by the daemon on every 401 of its own) means the token was revoked; any other 401/403 means a gate in front refused, and the app shows a sign-in prompt and retries once a minute without sockets. The daemon redacts `access_token=` from access logs.
- **Pairing = one-time codes.** A device never receives a token by being shown it. Instead a short-lived (5 min), single-use pairing code is shown as a QR for `<app-url>/pair#u=<daemon-url>&c=<code>` (the fragment never reaches a server), and the new device redeems it at `POST /v1/pair/claim` for its own fresh token. Two ways to get a code:
  - `muxtower pair` on the daemon's machine (first device). The daemon cannot know which address a device will use, so without `--url`/`public_url` it prints only the code (plus the addresses it can see, as hints) and the device enters it on whatever address it opened: the bundled UI pairs with its own origin (`/pair#c=<code>` or the inline code field). With a known address it also shows a QR code;
  - **from an already-paired device**: the app's "Add another device" shows one QR carrying a fresh code for every daemon it knows, so a phone that is paired once can pair a laptop in one scan. A photographed QR is useless once redeemed or expired.
- **Shared mode.** `pairing.mode = "shared"` makes claims hand out one existing named token instead, for setups where a front gate must already know every token it lets through.
- **Public URL.** `public_url` in config is what pairing and the bundled `/config.json` advertise; behind a proxy the daemon never guesses its own address from the request.

## CORS and origins

- Default `cors.allowed_origins = ["*"]`. This is safe because auth is bearer-only: no cookies are ever sent, so a foreign page can call nothing but `/v1/health` and `/v1/pair/claim` without a token. Listing origins only tightens it. `allow_credentials` is false; allowed headers are `Authorization`, `Content-Type` and whatever `cors.extra_headers` lists (a gate's own credential header, for apps that run off the daemon's origin); preflights are cached 10 minutes.
- Browsers do not apply CORS to WebSockets; `/v1/stream` checks `Origin` against the same list (any origin by default) and always requires the token.
- A reverse proxy or gate in front must let `OPTIONS` preflights through untouched, since they carry no credentials.
- The app never goes through a proxy of its own: a hosted app talks to daemons directly from the browser, so the host never sees tokens or terminal contents.

## HTTPS

HTTPS is the expected setup, not an extra: service workers, installing the PWA and Web Push only work in a secure context (localhost excepted). `muxtower serve` binds `127.0.0.1` by default and warns when it binds anything else while `public_url` is not `https://`. Documented ways to put HTTPS in front:

1. **Tailscale** (personal use): `tailscale serve --bg 8731` → `https://<machine>.<tailnet>.ts.net`, certificate managed by Tailscale, no domain or open port.
2. **Cloudflare Tunnel**: a public hostname, no open port, TLS at Cloudflare.
3. **Caddy** (own domain): `reverse_proxy 127.0.0.1:8731`, certificates issued automatically.

A hosted HTTPS app cannot reach a plain-HTTP or private-IP daemon (mixed content, Local Network Access); such daemons use their bundled UI.

## Hosting the app

The app is a static SPA; the same build runs anywhere.

- **Bundled** (recommended): served by `muxtower serve` at `/`, same origin as its daemon. The glasses app (`glasses/`) is bundled next to it at `/g2/`.
- **Your own static host**: one-click "Deploy to Cloudflare" (Workers static assets, SPA fallback via `not_found_handling`) or fork + GitHub Pages (Actions workflow; base path from `MUXTOWER_BASE`). Add daemons by pairing.
- **A public instance** run by the project, for convenience only. It is built and deployed by public CI from tagged releases, so users can check what they run; the docs still recommend the bundled UI, because whoever serves the JS could read the tokens in that browser.

## One entry per agent

A Claude Code process can be both a tmux pane and a Remote Control session. The process writes `~/.claude/sessions/<pid>.json`, whose `bridgeSessionId` (`session_<id>`) is its Remote Control session (`cse_<id>`). The capture loop looks for that file from each pane's process down (the pane may run a shell first); the directory then lists the agent once, under its tmux id, with the remote side's name, origin, summary and conversation. Text messages to such an agent go through Remote Control (structured, cannot land in a dialog); keys go to tmux.

## A session's name

The latest deliberate name wins (`sessions/naming.py`). A name muxtower gave it (at launch, or renamed in the app, or chosen by an agent starting a teammate) beats one its agent made up itself (Claude Code's `nameSource: "derived"`); a name the owner set on the agent's side (claude.ai, the Claude app, `/rename`: `nameSource: "user"`, with `nameSince`) newer than muxtower's beats it; a rename after that wins again. A Remote Control title other than the name Claude Code derived was set there by someone, at a time not known: it beats a launch name, not a rename. With nothing known of where the agent's name came from, only a rename counts. The rename dialog offers the agent's own name (`agent_name`).

## After a restart

A machine (or its tmux) that restarts takes its sessions' panes along. A session whose pane is gone is told apart (`sessions/interrupted.py`): ended when the tmux server it ran in is still there (its pane was closed), or is gone but this daemon saw it alive since it started (it was that server's last pane); interrupted otherwise (another server on its socket, none never seen, or a server not known), since when muxtower cannot tell it keeps the session rather than drop it. An interrupted session is kept with what starts it again, saved when it started: its options (never its first prompt, never a token; `option_values` says which take a value) and the agent's own id for its conversation (from its transcript's name). An adopted session is kept only when that id is known.

`[recovery] mode`: `ask` (default) lists them in the app, all ticked (and below `muxtower`'s status, where `muxtower attach` on one also starts it again), and pushes once; the owner starts again those they keep ticked, and the others wait in the Interrupted list, to start later or remove. `auto` starts them again as soon as they are found; `off` lets them go, as before. Each is started in its folder with its options and its conversation resumed (`resume`: `claude --resume <id>`, `codex resume <id>`), under its own id, so its name, marks, role, project and tasks stay with it; nothing is sent to it, so it does not carry on by itself (`recovery/`). The concierge goes the same way (it is not started anew while it waits). A node keeps and starts its own, the hub asking it over the link (`recover`). Headless Codex threads are resumed by Codex's app-server as before.

## Settings from the app

The app's Settings page changes features only (`settings/catalog.py`: after a restart, the concierge, summaries, voice input, Remote Control, Codex, usage alerts); what the daemon needs to start or what is secret (host, port, `public_url`, proxies, CORS, pairing, tokens, provider keys, the hub link) stays in the config file. A change is kept in the database (`settings_values`), over the defaults and under the config file: a key the file or the environment sets is shown as set there, and not changed from the app, so the two never disagree. Stored values go into `Settings` when the daemon starts, before anything reads them. Each says when it applies: `now` (read each time: put into the running daemon at once) or `restart` (shown as waiting until the daemon starts again). `GET`/`PATCH /v1/settings`, all or nothing, each change audited; `?node=NAME` reads or changes a node's over the link (`settings`, `set_settings`), and a node too old for them says so.

## The concierge (optional)

`[concierge] enabled` keeps one Claude Code session running on the daemon's machine for the owner to talk to instead of each session: it relays the owner's requests, reads and summarizes sessions, answers their prompts when the owner says so, starts new ones, and also answers ordinary questions. It is launched by muxtower in tmux (`--model sonnet`, its own instructions, Remote Control on by default so the Claude apps reach it too) with an MCP config that points at `/v1/mcp` with a token minted for it.

- Tools: `list_sessions`, `read_session`, `send_message`, `approve`, `deny`, `interrupt`, `start_session`, `watch_session`, `unwatch_session`, `list_events`. Plain-text results, short enough to relay. A session is described by three things kept apart (`mcp/describe.py`): the device it runs on (unknown when nothing places it, never the hub by default), what reaches it (muxtower on a device, through tmux or headless, or only the Claude account's Remote Control) and its harness (Claude Code from the CLI, the desktop app…, Codex); archived and hidden sessions only with `all`. `start_session` starts on the hub, or with `machine` on a node joined to it (the node's own launcher, so it needs tmux there).
- Watching: when a watched session finishes a turn, starts needing the owner or ends, muxtower sends the concierge one line per event (`concierge/events.py`): `[muxtower event #N · time]`, the session's id (it can rename itself; the name it was watched as is kept beside the new one), its state, the conversation items that are new since the previous event and the `read_session(…, after=…)` call that returns only those, what it asks or said. The hub keeps every event in SQLite (the latest 200), with whether it was sent: what is not sent yet is sent after a restart, what a watched session did while the daemon was down is told after it (each session's last state is kept), and `list_events(after=N)` catches the concierge up after its own restart. Text from the session (name, command, reply) is quoted as a JSON string, cut short and unable to open an event of its own: it is data, not the owner's words. Updates wait until the concierge is idle (never sent while it shows a prompt; after two minutes of it being busy, Claude Code queues them), and whatever waited goes as one message (its latest 20 events, with a pointer to `list_events` for older ones).
- Its instructions say that only the owner's messages are instructions; what it reads from sessions is data.
- Clients pin it (`role: "concierge"`); on the glasses, talking outside a session talks to it.

## Teams

Sessions can work as a team: the owner gives each a role (free text: muxtower does not read meaning into it, every project has its own), and sessions of a project find each other and hand each other work. Nobody dispatches; any session may.

- **A team is a project.** A team is all the sessions of one project: it has no name or fields of its own. A session's project and role are its own and stay as they are: an agent that cds elsewhere or edits files in another repository is still in the project it was in (and listed where it started).
- **Projects.** A session's project is worked out once, as soon as it is listed (`teams/placing.py`), on the machine its folder is on (`teams/checkout.py`), from the folder it started in: its origin remote (`owner/repo`, so one repository cloned at different paths or on different machines is one project), else its repository's top folder (its worktrees together), else the folder. A session elsewhere goes by its folder's name until something sets it. An agent or the owner can move a session to another project or rename a project for all its sessions; what was set is kept as set. Roles and projects are kept on the hub (`session_team`).
- **Reaching muxtower as itself.** A session muxtower starts gets muxtower's MCP server with a token of its own, `session.<id>.<hook token>`, written the way its hooks are (Claude Code: an `--mcp-config` file, mode 0600; Codex: `-c mcp_servers.muxtower…` with the token in its environment). The token opens `/v1/mcp` and nothing else, and dies with the session; a session started with its own `--mcp-config` (the concierge) keeps its own. A device's token is no session: `my_team` then says it cannot tell who is calling and lists every project.
- **Tools.** `initialize` returns instructions (call `my_team` first; no role, ask the owner or set the one they gave; decide yourself whom to ask by role and state; `[muxtower task from …]` messages are a teammate's work). `my_team` says who the caller is and lists its project's other sessions with role, device, state, folder, worktree and branch; `set_role` and `set_project` set them for the caller or, by `session_id`, for another.
- **Resuming.** Each session's record keeps the agent's own id for it, from its transcript's name (Claude Code's session id, Codex's thread id), so a session resumed under a new muxtower id is known as the one it was: `start_session(resume=<id>)` (`claude --resume <id>`, `codex resume <id>`) takes over its role and project, and so does a session resumed by hand once its transcript is known, unless someone gave it a role or a project already. `start_session` also takes `role` and `project`; `rename_session` and `archive_session` do what the app's menu does.
- **Where a session is listed.** One place each, under its device, by the folder it started in (`session.cwd`; where its agent works now, when deeper, is `working_dir`, shown beside it and never moving it): its project as kept (`session.project`, the same `my_team` says, with `project_auto` and `project_source`), unless that is only its folder's name; else its repository (`session.git`: its main folder, the worktree and branch it is in, its origin, read once per folder and cached on the machine the session runs on, `teams/checkout.py`; a desktop app's session on a node, which the hub lists from its own Remote Control, gets it from what the node reports of its processes, `nodes/processes.py`), whose main folder holds its subfolders and every worktree, a worktree as a line under it by its branch wherever its folder is (a submodule is a repository of its own); else its folder, in the folder tree, where a repository is one node under the folder it lies in. `my_team` goes by the same reading. The app does not work it out again (`sessions/model/places.ts`).
- **In the app.** Listed sessions carry `team_role`, `team_note`, `project`, `project_auto` and `project_source` as kept (no git is run to list them); `PUT /v1/sessions/{id}/team` sets them (only what is given changes), and `GET /v1/sessions/{id}/tasks` lists the tasks it was sent and sent, newest first.
- **Across machines.** Every session reaches the daemon on its own machine (the token is checked there, nothing is handed between machines). On a node, the team tools are asked of the hub over the link (protocol 2: the node asks too, `nodes/asked.py`), which answers as the node's session (`<node>~<id>`, so a node speaks only for its own sessions); when the hub is not linked or runs an older muxtower, the node answers for its own sessions and says so. A daemon that joined no hub answers itself.
- **Tasks.** `send_task(to, text)` hands work to a teammate: `to` is a session id, or a role of the sender's project that one session has (several: the error lists them, and the sender picks). It arrives as a message headed `[muxtower task from <name> (<role>) · <id>]`. `team_tasks` is the queue and one loop alone sends (`teams/tasks.py`): `send_task` checks the task, stores it held, wakes the loop and waits a moment (3 s) for what became of it (delivered; held, the receiver waiting on the owner; or queued). The loop goes through each receiver's held tasks in order, on a new task, every change of state and every 30 s: one on Remote Control gets them at once; one in tmux too (Claude Code queues them behind its turn), unless it waits on the owner (a prompt or a question), where typing would answer the prompt, and a task that cannot go (that, or a failed send) keeps the later ones to that receiver back. A restart goes on where it stopped; a node's sessions' tasks are the hub's to send. Each task is recorded (who, to whom, when, its first 200 characters, delivered, held or undeliverable; the latest 500), and `my_team` shows each member's last three. The record schedules nothing.

- **Who a message is from.** `send_message` types into a session at once and heads it `[muxtower message from <name> (<role>) · <id>]` (a device: `<device> (a device, not a session)`), added by the daemon from the caller's identity; a head the text brings is dropped first, so it is neither faked nor doubled (`mcp/sender.py`). What must arrive exactly goes without a head, still audited with its sender: a slash command on one line, and an answer to what the session asks now (it waits on a prompt, or the text is exactly a reply its next step offers). The owner typing in the app or a terminal is never headed. The concierge, which reaches MCP with a device token of its own, is its session: that token stands for the concierge's session id (`mcp/routes.py`), so `my_team`, `send_task` and `send_message` name it.
- **A node without its hub.** Team data is the hub's: while a node's hub does not answer, `set_role`, `set_project` and `send_task` are refused there ("nothing was changed"), not written on the node, and `my_team` answers from this machine, saying so. A standalone daemon (no hub) keeps its own. Rows a node wrote this way before stay in its table and are not used while it is joined: the hub's records are what the lists and the team tools say.
- **Two writers in one worktree.** When two running sessions of one machine write files in the same git worktree within `[writes] window_minutes` (30), each is told (`writes/`): a mark on its row (who, and the files both changed) and a line in `my_team` ("also writing in <worktree>: …"); one's commit could take the other's unfinished change along. A hint only: nothing is locked or held back, and it never moves a session or changes its project. Counted narrowly, as a false alarm is worse than a miss: only what file-editing tools report (Claude Code's Edit, Write, MultiEdit, NotebookEdit; Codex's apply_patch, when its hooks report it), each path resolved (symlinks too) to the worktree it is in (`git rev-parse --show-toplevel`): another worktree of the same repository, another machine, or a file outside git never counts. Bash commands are a known blind spot (a read cannot be told from a write). Kept in memory.

## Usage

Process facts (who started whom, a process's command line, folder, start and open files: what links a pane to its agent) come from /proc on Linux and from the kernel itself on macOS (`infra/libproc.py`: libproc and sysctl through ctypes), so a capture round runs no outside command; `ps` and `lsof` remain where the kernel will not tell, their answers kept a few seconds (`infra/procfs.py`).


muxtower should cost little, and show it. Every daemon samples what it uses every 5 s (`usage/`: /proc where there is one, the kernel's own calls on macOS, else the standard library; no outside command; a value it cannot read is null, unknown, never 0) and keeps it: CPU over the last minute and ten (not since it started, which flattens a spike), memory, threads, open files, its children (Linux), and the capture loop's ticks, with the screen rule that took longest and the session it read. `GET /v1/usage` lists this machine and each node, which reports its own over the link every 10 s (stale once that is old). Over `[usage]` limits (CPU 20% of a core, 200 ms a tick, 500 MB) is an alert: the app shows a small mark by the machine's name in the sidebar, opening to what, how much and the limit (a slow loop names its slowest rule), and the Daemons page lists every machine's usage. The app measures itself too (`lib/diagnostics.ts`: live frames and bytes a minute, how long a terminal takes to draw, the JS heap where Chrome tells), shown under Daemons › Diagnostics and as a mark by the app's name when over a limit.

## Reply summaries and voice

- **Summaries.** A reply longer than `summaries.min_chars` gets a few lines in its own language that keep what the owner must decide, commands proposed and failures. They are made by a coding agent CLI already logged in on the daemon's machine (`claude -p` with haiku, or `codex exec`), so a subscription is used instead of an API key. The CLI runs with no tools, settings or MCP servers in an empty directory, and gets the reply on stdin. Each reply is summarized once (keyed by its hash, cached in SQLite), in the background: when a client asks (`POST /v1/sessions/{id}/summary`) and, with `summaries.eager`, as soon as a session starts needing the owner. Sessions carry it as `reply_summary`; the stream pushes the list again when one is ready.
- **Voice.** `POST /v1/asr` takes a recording (WAV from the glasses; WebM/Opus or MP4 from the web app's microphone, sent under its own file name so the provider reads the format) and returns text through an OpenAI-compatible transcription API (Groq `whisper-large-v3-turbo`, OpenAI `gpt-4o-transcribe`). The key stays on the daemon; nothing is stored, and the audit log records only sizes. Each request carries a prompt written in Simplified Chinese with the current session names and common terms: Whisper follows the prompt's script (no Traditional characters for Mandarin) and spells those names right. The client shows the text and sends it only after the owner confirms.
- `GET /v1/me` lists which of these the daemon offers (`features`).

## Read state and hidden sessions

With many sessions running, the owner needs to see which finished turns they have not looked at yet: those are what to pick up next. The daemon keeps, per session, when it last finished a turn (`sessions/turns.py`) and when anyone last looked at it (`sessions/marks.py`, table `session_marks`), so every device agrees. A session is `unread` when it finished after the last look, when its source's own flag says so for activity since then (Remote Control's unread, shared with the Claude apps), or when the owner marked it unread to come back to. `POST /v1/sessions/{id}/read` (`{"read": false}` marks unread) is sent by a client when it opens a session, when an open session gets news, and every 30 s while it stays on screen; reading also marks the session read on Remote Control. A session looked at in the last 45 s gets no "done" notification: someone is watching it. The same store keeps which sessions the owner **hid** (`POST /v1/sessions/{id}/hide`): they leave every list and count, show only under "Hidden", and send no "done" notifications (a hidden session that gets blocked still alerts). Hiding keeps the agent running; **archiving** ends it (`POST /v1/sessions/{id}/archive`, after the owner confirms): its tmux pane closes (muxtower's own tmux session, for one it started), a Remote Control session is archived there too (first, so a failure changes nothing); a node's session that also runs Remote Control is archived there by the hub, since its node has none, and the session is kept to read under "Archived" (`sessions/archive.py`, table `archived_sessions`): its last view, and its conversation from the Claude Code transcript (the file outlives the process) or, without one, the items it had. An archived session is read-only (no screen, no input, no read state); `DELETE` deletes it from the archive. In the list, a resting unread session is its own status, "Finished, unread", between "Needs you" and "Working" (a check in the accent color, bold name); the list menu marks everything shown read, the session menu marks one unread.

## Hub and nodes

One daemon is the **hub** (the one that is always on, which phones use); other computers' daemons
(a Mac, a Windows machine, another server) join it as **nodes**. Their sessions are listed, driven,
approved and notified through the hub as if they ran there, so a phone pairs with the hub alone and
needs no address of a laptop's. Every daemon is both: a hub to whatever joins it, and a node of the hub it
joined, if any; a node keeps its own API and UI.

- **Joining**: on the hub, a pairing code (`muxtower pair`, or Daemons › Join a computer); on the node,
  `muxtower pair --join <hub> --code <code>`, which has the node's daemon redeem it at
  `POST /v1/nodes/claim` for a token of the node's own, kept in its state directory (`hub.json`, 0600).
  A node token opens the node's link and nothing else (it is in its own table, `nodes`, not a device
  token). Headers for a gate in front of the hub (`[hub] headers` in the node's config, e.g. the gate's
  API token) go with every request to it. `DELETE /v1/nodes/{name}` removes a node: its link is closed
  with 4401 and the node forgets the hub; `muxtower pair --leave` stops a node reporting.
- **The link** (`nodes/protocol.py`): one WebSocket the node opens to `/v1/nodes/link` (the token as a
  `bearer.` subprotocol), JSON frames both ways: requests and their answers (`{id, method, params}`,
  `{id, result | error{status, message}}`) and events. The node says hello (protocol version, name,
  version, what it can start), then reports its sessions whole on every change (debounced, and every
  minute regardless: idempotent, so a reconnect needs no catching up), conversation items as its own
  stream has them, and the screens the hub watches. The hub's requests are the API's own verbs
  (conversation, screen, input, approve, deny, resize, update, terminate, archive, mark read, detect
  folder, create, watch a screen); errors travel as statuses and come out as the same exception, so a
  409 on the node is a 409 from the hub. The node reconnects with backoff (1 s doubling to 30 s,
  jittered); either side restarts whenever it likes.
- **On the hub**, a node's sessions are one more session source (`nodes/source.py`), so read state,
  hidden, notification levels, placement, finished turns, push and the assistant work on them
  unchanged; what only a daemon can do (a screen, input as typed, resizing, renaming, stopping, starting
  one: `CreateSession.node`) goes to the node too (`nodes/directory.py`). Ids are `<node>~<its id>`,
  except a Remote Control session's, which is the account's wherever it is listed: reported by the hub's
  own Remote Control and by a node, it is one session, the node's when its agent runs there (`on_host`:
  the node has its process, terminal and transcript), else the hub's. A tmux pane that also runs Remote
  Control, on a node, is one entry there and hides the hub's copy, as on one daemon. Attention is
  announced when a node's report shows a session starting to need the owner (not on first sight).
- **Where a Remote Control session runs**: Claude Code keeps a file per process on its own machine
  naming its Remote Control session, so a node reports the ids, folders and entrypoints of those it runs
  (`running`, every few seconds when they change; `nodes/processes.py`) without listing them or reading
  a Claude login, and the hub lists its own copy as that computer's (machine, folder, origin; not
  `on_host`). One that no longer runs, in a folder of a kind of machine (`/Users/…`, `C:\…`), is taken
  for the one node of that kind (the hello says `sys.platform`), and a machine the owner typed that names
  a node ("Mac") is spelled as the node is. A node signed in to another account lists that account's
  sessions itself (`remote_control.enabled`; on macOS from the Keychain item Claude Code keeps).
- **Versions**: releases go to PyPI (a `vX.Y.Z` tag publishes one); daemons only tell each other their
  versions. Each side speaks link protocols `OLDEST`..`PROTOCOL`; a link speaks the older side's
  `PROTOCOL`, and the hub refuses a node only when that is older than either side still speaks
  (`protocol.agree`), so raising `PROTOCOL` alone asks no node to update and raising `OLDEST` does.
  The hub says its own version first on every link (`hub`), even to a node it is about to refuse;
  such a node installs the hub's version from PyPI (pipx, or pip
  outside pipx) and execs itself, the same pid, so a service manager sees no exit
  (`nodes/update.py`). A node that is only older is told (`HubStatus.update`, `NodeInfo.update`), and
  follows every update with `hub.update = "always"`. Never downgrades; a source checkout installs
  nothing; a failed install (PyPI can serve a release minutes late) is tried again ten minutes later.
- **Forks and side chats**: a Remote Control session can come from another (`sources/remote_control/lineage.py`, read once when it is first seen). A fork made by Claude Code is tagged with its parent (`remote-control-fork-parent:`); Claude desktop's side chat ("ask on the side") starts with a copy of its parent's history, written at one instant under the same message ids, then a note that the owner forked it to ask something on the side. Its parent is the oldest listed session starting with the same message that is neither a side chat nor a tagged fork (a session whose history was uploaded at once when Remote Control was turned on midway is the oldest, so nobody's copy). A side chat of a session compacted since starts after its summary, so its first message is not the parent's: its parent is then the newest older session with its title (a side chat keeps its parent's). Claude desktop's fork has no tag, and one made from a message deep in its parent starts at that message: for a copy no first message places, the older sessions with its title are searched once (newest first, their first pages of events) for its first message, and only the one that holds it is the parent, so an equal title alone never makes one. `Session.fork_of` names the parent as listed (a parent in tmux under its tmux id, also for one fetched alone and for an archived fork) and `side_chat` says which kind; a fork in tmux that also runs Remote Control takes both from its remote side, and an archived one keeps them in its last view. The app folds side chats under their parent's row ("2 side chats · 1 unread", opening to a short line each); one that needs the owner stays in the list; forks are listed under their parent as a tree, the way Claude desktop shows them (indented, joined by └, a fork of a fork under its own parent; `model/forks.ts`), open by default, folded by the "N forks" line under the parent, which stays open while one of them needs the owner; a fork whose parent is not listed stays a row of its own, marked "Fork"; a session page says "Side chat of …" or "Fork of …", a link to the parent.
- **Offline**: the node's last report is kept in SQLite, so while it sleeps or the hub restarts its
  sessions are still listed, marked `offline`, read only (no capabilities, no alert), until it is back.
- **Accounts**: each daemon says which account its agents run as (`agents/accounts.py`, from the
  agents' own login files, who only: a claude.ai email, a ChatGPT email, or "API key"); the app shows it,
  and offers it as a filter and a grouping, only when sessions run as more than one.

## When the hub is down

The app reaches a hub's nodes directly while the hub does not answer (its machine restarting), and goes back to it when it answers with its nodes linked again (`nodes/direct.py`, `app/src/lib/daemons/fallback.ts`). Not a second hub: nothing is synced, team data stays the hub's (a node refuses to change it alone), push stays the hub's.

- **Addresses.** A node reports where the app reaches it in its hello (`url`: its `public_url`, else what `tailscale serve status --json` serves its port at; https only, as an https page cannot call http). The hub keeps it per node (`reported_url`), and the owner may set another (`PATCH /v1/nodes/{name}` `direct_url`). muxtower provisions no ingress.
- **Tokens.** While the hub answers, the app asks it for each node's address and a device token there (`POST /v1/nodes/direct`, every half hour): the hub asks each connected node over the link (`mint_token`, named `direct:<device>`; a new one replaces the last; a node makes no token of another name). Revoking a device on the hub revokes them (`revoke_token`), and a node away then is told when it links again (`node_revocations`).
- **Origins.** A node answers its hub's origin (from the link it joined) besides `cors.allowed_origins`, and Chrome's Private Network Access preflight (a tailnet name is a private address).
- **In the app.** Each node handed over is a daemon in the same paired list, marked `via` its hub, used only while the hub is down (`isActive`): its stream, lists and actions are those of any daemon. A hub is down when its stream has been down for 8 s and a probe gets no answer (a 401 or a sign-in gate is an answer: then there is nothing to go around); it is probed every 15 s. The open session follows (a node's `<node>~<id>` on the hub, `<id>` on the node), with its draft. The service worker answers a reload of any page with the cached app, so a reload while the hub's machine is down still shows it.

## Push

Web Push with a per-daemon VAPID key. A browser registration holds one subscription, so the app registers its service worker once per daemon (scope `<base>push/<daemonId>/`, same script). The subscription belongs to the app's origin; the notification payload carries `daemon_id` and `session_id`, and a click opens `/d/<daemon>/s/<session>`: in the app already open, the worker asks it to go there (`postMessage`, `useNotificationClicks`), since a daemon's registration does not control the app's pages and cannot navigate them. Filters per subscription: which states notify, whether finished turns do (`done`, on by default), muted sessions; and per session, the owner's level (below). A subscription belongs to the paired device that registered it: once that device is revoked, the daemon drops it at the next push instead of sending. The app registers its subscription again on every start, which keeps the daemon's copy current and ties older ones to their device. Registering a fresh worker waits for that registration's own worker to activate (`navigator.serviceWorker.ready` is the page's root registration).

Two kinds of notification, both one per session (a newer one replaces the older, so a handled approval gives way to "Done"):

- **attention** — a session entered a state that needs the owner. Stays on screen until dismissed or settled.

A notification goes once its session is **settled**: seen (not `unread`) and answered (not `needs_attention`). A push cannot be sent only to take one away (iOS revokes a subscription whose pushes show nothing, Chrome shows a notification of its own), so: the app closes the ones it sees settled, by news newer than the notification, when its sessions change and when it comes to the front (`useCloseSettledNotifications`); and every push names the sessions notified before that are settled since (`settled`, `notify/service.py` remembers the last 64 notified for a day), whose notifications the worker closes as it shows the new one.
- **done** — a session finished a turn: `sessions/turns.py` sees it busy for at least 5 s, then idle for 6 s (a screen read can flicker; a pause to ask is covered by the attention alert, and sessions seen at startup are only learned). Not sent for the assistant, whose replies are the conversation itself.

Each session also has the owner's own level (`notify` on the session, `PUT /v1/sessions/{id}/notify`, kept in `session_marks` so every device agrees), set from its "⋯" menus: **all** (the default), **needs** — only when it needs the owner: attention as usual, and a finished turn only when its turn summary asks for them (`needs_action`, or status `need_input`; Remote Control writes the summary just after the turn, so the dispatcher waits up to a minute for it, and a session without one sends no "done"); such a turn also reaches devices that take no other finished turns — or **off**. It is meant for a session that checks on something every few minutes (`/loop`), whose every quiet round would otherwise be a "Done".

The text (`notify/text.py`): the title is the session's name, like a message's sender; the body starts with what is wanted or what happened — "Approve Bash: npm run build", "Question: …", "Plan ready for review", "Error: …", "Done: <what it did>", or "Done, waiting for you: <what it left>" from Remote Control's turn summary — then where it runs ("nas · ~/projects/web"). Markdown is flattened to one line.

- Names: a tmux session running Claude Code goes by the name Claude Code gives it (its process file's `name`, what `/rename` set), not by its tmux session's, unless the owner named it in muxtower (on starting it or by renaming; kept as `named`); one also on Remote Control goes by its title there.
- History of full-screen agents: Claude Code with `tui: fullscreen` draws on the terminal's alternate screen, so tmux keeps no scrollback and the terminal view can only show the visible screen. Every tmux session whose Claude Code writes a transcript (`~/.claude/projects/<cwd as dashes>/<sessionId>.jsonl`, found through its process file) has a conversation read from that file (`sessions/transcripts.py`: its last 3 MB at first, then followed every 1.5 s and pushed on the stream), also when it runs Remote Control, since the transcript holds the whole history. Sessions report `alt_screen`; their terminal view shows a bar that switches to the conversation.
- Layout follows the width: phones show one pane at a time with bottom tabs; from `md` the list and the session sit side by side; from `lg` a sidebar adds the views, each device with its folders (foldable), and the sources, with their counts. The list's view, scope, grouping and search live in the URL; going back lands on the same list at the same scroll position.
- Terminal cells: non-ASCII characters get exactly the cells tmux counts (wide characters a centered two-cell box), so the grid holds whatever font a device falls back to. Fit measures one line of the real font and line height; when lines overflow and fit is off, the view offers "Fit width".
- No configuration is baked into the bundle. An optional `/config.json` (`{"daemons": [{name, url, token?}], "acknowledge_public_tokens"?}`) next to `index.html` supplies default daemons, written at build time from `MUXTOWER_APP_CONFIG`; a preset token requires the acknowledgement and shows a warning. The bundled copy served by the daemon advertises its own daemon.
